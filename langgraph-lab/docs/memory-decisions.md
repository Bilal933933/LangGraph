# قرارات الذاكرة (Memory Decisions)

> المعتمد بعد مراجعة الكود الحالي. يثبت القرارات فقط.

## 1. ثلاثة أنواع تخزين (منفذة)

| النوع | المكان | الدور | الخلود |
|-------|--------|-------|---------|
| الحالة الحية | ذاكرة العملية (RAM) أثناء `invoke` | تنفيذ العقد | لا — تتبخر بعد `END` |
| اللقطات | `Checkpointer` (`InMemorySaver` / `PostgresSaver`) | استئناف الخيوط + حالة `ChatState` كاملة | نعم — لقطة بعد كل عقدة |
| الأرشيف | قاعدة البيانات (`conversations`, `messages`) | سجل العرض والقوائم والبحث | نعم — جداول دائمة |
| النافذة | لحظية عبر `select_window(limit=20)` | ما يراه LLM فعلًا | لا — مشتقة كل مرة |

## 2. القرارات المعتمدة (الحالية)

- **الخلود عبر `Checkpointer` دائما**: من يخاف الانقطاع لا يعتمد على الذاكرة أبدا.
- **Postgres للإنتاج**: قاعدة واحدة لبيانات العمل واللقطات (نسخة واحدة ونسخ احتياطي واحد) عبر `setup_postgres_tables()`.
- **التطوير محليا**: `InMemorySaver` للسرعة عند غياب `DATABASE_URL`.
- **لا `SqliteSaver` ولا `Redis` حاليًا**: مؤجلة حتى حاجة فعلية.
- **توقيت اللقطة**: بعد كل عقدة تنتهي (بعد دمج المخفضات)، لا عند الرد النهائي فقط.
- **القراءة من اللقطات**: عند `invoke` بنفس `thread_id` (`t{user}:c{conv}`).
- **جدول `Message` للعرض فقط**: لا يُعاد حقنه في الرسم وإلا تضاعف مع `add_messages` — المصدر الوحيد للاستمرارية هو `Checkpointer`.
- **`Checkpointer` ليست نافذة السياق**: الأولى أرشيف كامل بلا سقف، والثانية آخر 20 رسالة لكل استدعاء.
- **الهوية من الخارج**: `teacher_id` من المصادقة/المالك، لا من LLM — والملف يُجلب حتميًا عبر `TeacherProfilePort`.

## 3. حقن الأوامر (موضع الخطر الحقيقي)

- مدخلات المعلم موثوقة نسبيا؛ الخطر في إجابات الطلاب بمرحلة المصحح.
- العلاج الحالي: فصل صارم بين التعليمات والمحتوى في الـ Prompt + مخرجات مهيكلة يتحقق منها Pydantic (`IntentResult`, `QuizRequest`, `LessonRequest`, `ProfileInfo`).
- مكتبات الأمان (`NeMo Guardrails` وأشباهها) تؤجل حتى تظهر حاجة فعلية.
- ملاحظة: `LLM Guard` مؤرشف للقراءة فقط منذ يوليو 2026 — لا يعتمد.
